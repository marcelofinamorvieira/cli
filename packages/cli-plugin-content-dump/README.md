# DatoCMS content dumps

DatoCMS CLI plugin to export an environment's content to a dump file, and to import a dump into an empty sandbox environment that has the same schema.

# Usage

```sh-session
npm install -g datocms
datocms plugins:install @datocms/cli-plugin-content-dump
datocms content:export --help
datocms content:import --help
```

A dump holds every record of an environment, every upload with its metadata, every upload folder and, with `--include-assets`, the file of every asset. Each record is kept with its published version and its newer draft, if it has one, with its blocks, links, tree parent, position, workflow stage and schedules. The dump also holds the environment's schema, which the import checks the destination against and reads to write the content: it writes content, not models or fields.

## Exporting

```sh
datocms content:export --environment=main --include-assets
```

This writes `main-20261015T094500Z.dump.zip` (the environment and the UTC time) to the current directory. `--out` names another file. An existing file is never overwritten, and an export that fails or is interrupted leaves no file behind.

- Use a token that can read every model and every upload, such as the project's full-access API token. The export holds only what its token can read.
- The export takes no lock. Keep the environment unchanged while it runs, or export a fork of it.
- Without `--include-assets`, the dump keeps each asset's URL instead of its file, and importing it needs the project to still serve that file.
- The asset CDN refuses to serve video files while the project setting "Block serving URLs for raw video assets" is on, which is the default. To export the files of video assets, or to import them from their URL, turn it off in Project settings > Asset CDN settings, and turn it back on afterwards.

## Importing

```sh
datocms content:import ./main-20261015T094500Z.dump.zip --environment=restore
```

The destination must be a sandbox environment (the primary environment is refused) that has the dump's schema and no records, uploads or upload folders. One way to have one at hand is to keep an environment without content, forked before the project had any content or emptied once, and to fork it for every import:

```sh
datocms environments:fork empty restore
```

Once an import is checked, it can be promoted with `datocms environments:promote restore`.

### The schema check

Before writing anything, the import checks that the destination has the dump's schema, comparing:
- the locales;
- every model and block model by ID, with its API key and each field's API key, type, localization and validators;
- the settings of each model that decide how its records are written: singleton, sortable, tree, draft mode, saving invalid drafts, all locales required and its workflow;
- the workflows and their stages.

Names, hints, appearance, fieldsets, default values, field IDs, the timezone and the environment's settings are not compared. Neither is the model the native migration runner records its migrations in (`schema_migration`, or the profile's `migrations.modelApiKey`), whose records the import leaves out.

When the schemas differ, the import lists the differences and says how to give the destination the dump's schema. If the dump was exported from an environment of the same project that still exists and still has the dump's schema, it prints the commands that copy that schema with a migration generated by the native CLI:

```sh
datocms migrations:new copyDumpSchema --autogenerate=main:restore
datocms migrations:run --source=restore --in-place --migrations-dir=<a directory holding only the generated script>
datocms content:import "./main-20261015T094500Z.dump.zip" --environment=restore
```

The generated migration creates models and fields with the IDs they have in `main`, which the import relies on. Before running it:
- the migration commands need a `datocms.config.json` profile (`datocms link` creates one), with the same `--profile` or `--api-token` as the import;
- move the generated script out of your migrations directory into a directory of its own, so that `migrations:run` runs it alone and your other environments never run it;
- if the script creates the `schema_migration` model, remove that part: `migrations:run` creates that model itself.

If the original environment no longer exists, or its schema has changed since the export, the message says so: a migration generated from any other environment that has the dump's schema works the same way. A dump can be imported only into the project it was exported from, because the import keeps the dump's model IDs and generated migrations copy a schema only between environments of one project.

### What the import writes

1. The upload folders, parents first, at their positions.
2. Every upload, from the file in the dump, or else from the original file at the asset's URL.
3. Every record, with its blocks, creation date and first publication date. A record is created only once the records it links to, its tree parent and the sibling before it are written (and published, when they are published), and it is published right after it is created when the dump has it published. This is the order the CMA requires, and creating siblings in order rebuilds the order of sortable and tree models. When records link to each other in a cycle, some are created with their linking fields empty, and those fields are written once every record exists.
4. Then the newer drafts of records that have unpublished changes, workflow stages, and the scheduled publications and unpublishings still to come.

Records, blocks, uploads and upload folders keep their IDs, so links and references keep working. The exception is legacy numeric IDs, which older projects still have and the CMA no longer accepts for new entities: each of them gets a UUID derived from it, used everywhere it is referenced, and the same in every import of the dump.

Uploads and records are written 8 requests at a time, and the CMA client waits out rate limits on its own. A record costs one request, one more to publish it, and one more for a newer draft.

Before the first write, the import also refuses a dump holding records that DatoCMS itself reports as invalid (for example records that a validator added later no longer accepts), listing them, since the CMA would refuse to import them.

The import does not keep version history, record and asset creators, update and publication times other than the first one, the exact position numbers of records (only their order), or scheduled publications and unpublishings whose time has passed. A schedule limited to some locales comes back as a schedule for the whole record. Every write triggers the project's webhooks and build triggers like an edit does.

### Failures and interruptions

The first error stops the import, naming the step and the CMA's error. Nothing is undone or resumed: the destination keeps what was written so far. Destroy it with `datocms environments:destroy restore`, fix the cause, and import into a new empty sandbox environment. Interrupting the import with Ctrl-C stops it the same way.

### Limits

- Records whose required link fields point to each other in a cycle cannot be created in any order. The import creates one of them with that field empty, which the CMA refuses; when the model saves invalid drafts, it refuses instead to publish that record, if the dump has it published.
- A field with a default value that a record emptied after it was created comes back with the default value: the CMA applies the default to an empty value on create.
- A generated migration cannot create a model under a legacy numeric ID, so the schema advice cannot help a destination that lacks such a model: fork the destination from an environment that has it.

## Output and errors

Both commands print their progress on stderr and a summary on stdout. With `--json`, `content:export` returns the dump's manifest with its `path`, and `content:import` returns `{ environment, counts, skippedRecords, skippedSchedules }`.

| Code | Meaning |
| --- | --- |
| `ENVIRONMENT_NOT_FOUND` | The environment does not exist in the project. |
| `OUTPUT_EXISTS` | The file `content:export` would write already exists. |
| `ASSET_DOWNLOAD_FAILED` | `content:export` could not download an asset's file. |
| `INVALID_DUMP` | The file is not a dump written by `content:export`, or it is damaged. |
| `PRIMARY_ENVIRONMENT` | `content:import` was given the primary environment. |
| `SCHEMA_MISMATCH` | The destination does not have the dump's schema. |
| `INVALID_RECORDS` | The dump holds records that DatoCMS reports as invalid. |
| `IMPORT_FAILED` | A write, or the download of an asset's file, failed during the import. |

## `@datocms/cli-plugin-content-dump content:export`

Export an environment's content to a dump file: every record (with its published version and newer draft), upload and upload folder, and optionally every asset file

```
USAGE
  $ @datocms/cli-plugin-content-dump content:export [--json] [--config-file <value>] [--profile <value>]
    [--api-token <value>] [--log-level NONE|BASIC|BODY|BODY_AND_HEADERS] [--log-mode stdout|file|directory] [-e <value>]
    [--out <value>] [--include-assets]

FLAGS
  -e, --environment=<value>  [default: primary] ID of the environment to export, or "primary"
      --include-assets       Also store the file of every asset, so the dump does not depend on the project serving them
      --out=<value>          Path of the dump file to write (defaults to <environment>-<UTC timestamp>.dump.zip in the
                             current directory)

GLOBAL FLAGS
  --api-token=<value>    Specify a custom API key to access a DatoCMS project
  --config-file=<value>  [default: ./datocms.config.json, env: DATOCMS_CONFIG_FILE] Specify a custom config file path
  --json                 Format output as json.
  --log-level=<option>   Level of logging for performed API calls
                         <options: NONE|BASIC|BODY|BODY_AND_HEADERS>
  --log-mode=<option>    Where logged output should be written to
                         <options: stdout|file|directory>
  --profile=<value>      [env: DATOCMS_PROFILE] Use settings of profile in datocms.config.js

DESCRIPTION
  Export an environment's content to a dump file: every record (with its published version and newer draft), upload and
  upload folder, and optionally every asset file

EXAMPLES
  $ @datocms/cli-plugin-content-dump content:export

  $ @datocms/cli-plugin-content-dump content:export --environment=staging --include-assets --out=./backups/staging.dump.zip
```

_See code: [lib/commands/content/export.js](https://github.com/datocms/cli/blob/@datocms/cli-plugin-content-dump@4.2.1/packages/cli-plugin-content-dump/lib/commands/content/export.js)_

## `@datocms/cli-plugin-content-dump content:import DUMP`

Import a dump written by content:export into an empty sandbox environment that has the dump's schema: no records, uploads or upload folders

```

    <value>] [--api-token <value>] [--log-level NONE|BASIC|BODY|BODY_AND_HEADERS] [--log-mode stdout|file|directory]

ARGUMENTS
  DUMP  Path of the dump file

FLAGS
  -e, --environment=<value>  (required) ID of the empty sandbox environment to import into

GLOBAL FLAGS
  --api-token=<value>    Specify a custom API key to access a DatoCMS project
  --config-file=<value>  [default: ./datocms.config.json, env: DATOCMS_CONFIG_FILE] Specify a custom config file path
  --json                 Format output as json.
  --log-level=<option>   Level of logging for performed API calls
                         <options: NONE|BASIC|BODY|BODY_AND_HEADERS>
  --log-mode=<option>    Where logged output should be written to
                         <options: stdout|file|directory>
  --profile=<value>      [env: DATOCMS_PROFILE] Use settings of profile in datocms.config.js

DESCRIPTION
  Import a dump written by content:export into an empty sandbox environment that has the dump's schema: no records,
  uploads or upload folders

EXAMPLES
  $ @datocms/cli-plugin-content-dump content:import ./main-20261015T094500Z.dump.zip --environment=restore
```

_See code: [lib/commands/content/import.js](https://github.com/datocms/cli/blob/@datocms/cli-plugin-content-dump@4.2.1/packages/cli-plugin-content-dump/lib/commands/content/import.js)_

# Development

```sh
npm run build
npm run typecheck
npm run typecheck:test
npm test
npm run test:integration
```

`npm test` needs no network or credentials: it runs the export and the import against an in-memory CMA. `npm run test:integration` exports and imports a populated throwaway DatoCMS project, created and destroyed with the account credentials described in the repository's `.env.sample`, and follows the schema advice with the native CLI (it needs `packages/cli` built). See [docs/design.md](https://github.com/datocms/cli/blob/main/packages/cli-plugin-content-dump/docs/design.md) for how the plugin works.
